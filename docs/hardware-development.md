# Develop and reboot on the MacBook Air

The current host is a MacBookAir7,2 running Ubuntu through UEFI GRUB. Linux
can supply the PCI/USB inventory, USB descriptors, HID report descriptors and
ACPI tables while we edit, build and test SrvrOS here. Rebooting into SrvrOS is
still necessary to validate firmware handoff, controller timing and real input.

## Confirmed hardware baseline (2026-10-16)

Release `c02ec72ad1c8f3d4` boots to the monitor on the MacBookAir7,2 and accepts
built-in keyboard input. The user confirmed typing works, then supplied a photo
of the `xhci` command: Apple `05ac:0291` is on port 5, slot 7, configured with
interface 1, DCI 5 and a 64-byte endpoint. Its stage is `ready`; the live dump
shows 27 interrupt completions and 27 HID reports. Port 5 is connected and
enabled. The installed release state independently identifies this build as
current and `ad2f72b629a8797a` as previous.

This confirms basic keyboard input after the port discovery/reset corrections.
It does not establish exhaustive key coverage, repeat-boot reliability or Apple
trackpad support. The two mouse-class devices in the dump are on ports 1 and 2;
the Apple composite device is currently configured only for its keyboard
interface. The earlier zero counters above the prompt are a startup snapshot;
the later `xhci` command shows the reports generated by typing.

## What Linux has established

The internal keyboard/trackpad is USB device `05ac:0291`, on root port 5 of
Intel xHCI `8086:9cb1` at `00:14.0`. Its configuration has three interfaces:

| Interface | Type | Interrupt IN endpoint | Max packet | Interval |
| --- | --- | --- | --- | --- |
| 0 | HID, non-boot | `0x81` | 64 bytes | 8 |
| 1 | HID boot keyboard | `0x82` | 64 bytes | 8 |
| 2 | HID boot mouse / Apple trackpad | `0x83` | 64 bytes | 1 |

Linux binds usbhid to interfaces 0/1 and bcm5974 to interface 2. The descriptor
intervals are raw USB values. Keyboard enumeration and basic reports are the
first target; the Apple trackpad protocol is a separate task. SrvrOS currently
selects one interrupt input interface per USB device, which also limits combined
keyboard/trackpad support.

`8086:9cba` at `00:16.0` is MEI. It was incorrectly used by the experimental SPI
driver and custom QEMU model. The kernel now matches GSPI `8086:9ce6` and checks
PCI class `0c80`, but the transport is disabled unless explicitly requested with
`srvros.spi=experimental`. That option is for investigation, not evidence that
the controller initialization works. The custom emulator still needs its
identities and assumptions corrected; its old SPI tests are not a hardware oracle.

The first physical test reached the monitor but accepted no built-in keyboard
input, including during the boot input probe. An external keyboard was not tried.
The user force-rebooted back into Ubuntu. This confirms the loader/kernel boot
path, but not keyboard or trackpad support.

The subsequent xHCI changes negotiate optional BIOS/OS ownership before reset,
allocate the advertised scratchpad buffers, reset connected USB2 devices even
when firmware left their ports enabled, wait 10 ms using MFINDEX after reset,
and program interrupt interval/Max ESIT Payload correctly. Polling leaves xHCI
interrupt delivery disabled, uses DMA ordering barriers, requests short-packet
events, and does not poll endpoints whose setup failed. These fix identified
code defects; the cause of the physical failure is not yet established.
Ownership/reset waits remain bounded iteration budgets, not calibrated wall-clock
timeouts. SuperSpeed companion parsing and full composite keyboard/trackpad
support remain separate work.

## Capture evidence from Ubuntu

```sh
python3 tools/capture_linux_hardware.py
# Include protected ACPI tables, in a new timestamped output directory:
sudo python3 tools/capture_linux_hardware.py
```

The collector writes under `build/hardware/<timestamp>`. It reads inventories,
descriptors and ACPI tables; it never opens input event streams or unbinds a
driver. `capture.json` records unavailable reads. USB descriptors can contain
device identifiers, so review a capture before sharing it publicly. The initial
unprivileged capture is `build/hardware/20261016-012726`; both Apple HID report
descriptors were readable, while 17 ACPI table reads need root.

## Build and install a GRUB entry

```sh
tools/host-env.sh make -j2 hardware-stage
# Optional repeatable UEFI GRUB -> Limine -> SrvrOS rehearsal:
tools/host-env.sh make hardware-smoke
sudo python3 tools/hardware_boot.py install
```

Use these commands from the repository root. The installer requires Linux,
UEFI, a writable FAT ESP mounted at `/boot/efi`, GRUB tools, and Secure Boot
disabled/unsupported. This Mac reports that Secure Boot is unsupported. The
rehearsal additionally uses `grub-mkstandalone` from the host's GRUB EFI tools.

The stage contains the kernel, initramfs, pinned Limine EFI loader, versioned boot config
and a SHA-256 manifest. Its identifier is derived from the payload hashes and
configuration version. Installation verifies both the source and copied files,
then adds `/etc/grub.d/42_srvros` and regenerates GRUB. Ubuntu's existing default
and firmware boot order remain unchanged; the menu becomes visible for five
seconds. No reboot is performed by the scripts.

Installed files live only under `/boot/efi/EFI/srvros/<release>/`, alongside
Ubuntu's loader. Each release occupies about 260 MiB. A successful update retains
the current and previous release, deleting only an obsolete release recorded by
this installer. Updating needs room for three releases temporarily; this laptop's
1 GiB ESP has sufficient space at the initial inspection. The installer restores
the prior GRUB snippet and generated config if regeneration/validation fails.
This recovery does not make a FAT update immune to power loss.

Select **SrvrOS (current, RAM filesystem)** from GRUB. After a second distinct
installation, **SrvrOS (previous, RAM filesystem)** is also available. To select
SrvrOS for just the next boot, once the menu has been installed:

```sh
sudo grub-reboot srvros-current
# Reboot when ready; save any Ubuntu work first:
sudo systemctl reboot
```

GRUB's one-shot selection is consumed before SrvrOS starts. On subsequent boots,
Ubuntu remains the default. If SrvrOS hangs, restarting the laptop returns to the
GRUB menu. The original release reached the monitor on this laptop; the revised input
driver still needs a physical retest.

## Filesystem and logs

A `.exfat` file is data, so GRUB cannot execute it as an OS. This entry chainloads
Limine, which loads `srvros.elf` plus `initramfs.tar`. The initramfs includes the
built `srvros.exfat` image, mounted at `/fat` in RAM. The entry supplies
`srvros.storage=ram`: the kernel skips AHCI initialization, registers no AHCI
disks, and uses the in-memory filesystem. Other existing ISO/QEMU entries retain
their normal storage behavior.

Changes to `/fat`, including `/fat/var/log/boot.log`, disappear on reboot. The
kernel's "persisted" bootlog message means it wrote to that RAM filesystem;
it does not mean the log reached the laptop's SSD. For early failures, use the
visible debug output and a photograph/video. Durable diagnostic capture needs a
separate storage/network/serial plan. There is currently no SrvrOS USB mass-storage
driver, so booting from a stick does not itself provide runtime USB log storage.

New hardware stages add `srvros.inputdiag=1`. After startup the display is cleared
and a compact **USB INPUT DIAGNOSTIC** remains above the prompt. If keys still
fail, photograph that whole screen. It shows firmware handoff, controller setup
stage, scratchpad count, connected ports, selected interface/endpoint, completion
code, and report counts from the earlier input probe. Each root port also shows
its connection/enable state, reset outcome and attempt count, plus initial,
reset-completion and current PORTSC values. A `no-connect`/`debouncing` result
means enumeration never reached a reset; `reset-timeout` means it was requested
but completion was not observed; `ready` means reset and recovery succeeded. It is a snapshot at monitor
entry, not a live counter display. Try an external USB keyboard as a comparison
if one is available; plug it in before boot because hotplug enumeration is not
implemented. Do not treat the expected Apple port/interface line as detection.

When input works, `bootinfo`, `hwdiag`, `xhci` and `dmesg 512` in the monitor
help narrow the failing stage. Check the monitor's `help` output for commands.

## Bootloader path detail and verification

GRUB EFI chainloading must set `root` to the ESP before loading Limine. The
[GRUB chainloader](https://github.com/rhboot/grub2/blob/master/grub-core/loader/efi/chainloader.c)
creates separate directory and filename device-path nodes.
[Limine 11.4.1's configuration lookup](https://github.com/Limine-Bootloader/Limine/blob/v11.4.1/common/lib/config.c)
uses the first file-path node and strips its final component. The release layout
therefore puts the EFI executable in `loader/`, with identical `limine.conf`
files there and one level above. This supports the split GRUB path and the normal
single-node firmware path without writing a shared config into the ESP root.

`make hardware-smoke` builds a disposable GPT/FAT32 ESP with a standalone GRUB,
uses the same generated menu and staged files, boots through OVMF, checks RAM
storage and SPI-disabled markers, and types `echo grub-usb-ok` through an emulated
USB keyboard. Logs are `build/review/hardware-grub-serial.log` and
`hardware-grub-qemu.log`. This verifies the loader workflow and QEMU input,
not the Apple controller or trackpad. `make test-xhci` compiles the real driver helpers on the host and checks the
captured Apple descriptor, 32/64-byte endpoint contexts, interrupt scheduling,
scratchpad counts and allocation failure cleanup, ownership timeout, and short
packet TRB flags. Its MMIO model exercises the actual root-port discovery/reset
code with delayed connection and reset acknowledgement, stale completion flags,
MFINDEX wrap, reset timeout, disconnect, stalled clock, and an already-enabled
SuperSpeed port. Discovery observes ports for at least one second and requires
100 ms of stable connection; reset waits for a fresh PRC completion and allows
10 ms of recovery before enumeration. This is bounded boot discovery, not runtime
hotplug support. QEMU does not reproduce Apple firmware or Intel scratchpad
requirements. Primary references for the implemented fields/sequence are
[Linux xHCI allocation and endpoint setup](https://github.com/torvalds/linux/blob/master/drivers/usb/host/xhci-mem.c)
and [Linux firmware handoff](https://github.com/torvalds/linux/blob/master/drivers/usb/host/pci-quirks.c).
PORTSC neutral writes and change-bit semantics follow
[Linux xHCI root-hub handling](https://github.com/torvalds/linux/blob/master/drivers/usb/host/xhci-hub.c)
and [port register definitions](https://github.com/torvalds/linux/blob/master/drivers/usb/host/xhci-port.h).

Installer unit tests cover retention,
repeat deployment, interrupted first installation, rollback on regeneration
failure, corrupt payloads, refusal to overwrite unmanaged files, and updating
from the previous boot-config version while preserving its fallback entry:

```sh
python3 -m unittest discover -s tools -p test_hardware_boot.py -v
```

To remove the menu entries while retaining installed payloads for inspection:

```sh
sudo chmod -x /etc/grub.d/42_srvros
sudo update-grub
```

A subsequent install reenables the snippet. The installer does not replace
Ubuntu's EFI files or run `grub-install`/`efibootmgr`.
